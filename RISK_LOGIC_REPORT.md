# Risk Logic Report

Audit date: 2026-07-18

Scope: Current risk, execution, protection, and exit-management logic in `D:/okx/harmonic_agent`.

## Summary Verdict

Current risk logic is capital-preserving and protection-first. It has several strong controls before and after entry:

- Market ownership blocks cross-mode duplication.
- Performance block prevents mature losing modes from continuing.
- Confidence sizing uses PF, win rate, sample count, and category.
- RR and minimum profit room are checked against the live price.
- Expected edge must exceed fees/slippage and minimum net profit.
- Risk-based leverage cap keeps planned loss near configured max.
- New entries pause if any active/live position lacks verified TP/SL.
- Filled orders must receive exact-fill protection or the engine triggers emergency close/halt.

The main weakness is not the absence of safety gates. The main weakness is insufficient measurement of how each gate affects opportunity quality and long-term expectancy.

## Entry Risk Flow

1. Market router must allow the mode.
2. Candidate must be generated by harmonic scan or direct mode setup.
3. Entry must be near the setup PRZ or mode-specific trigger zone.
4. HTF trend filter must pass.
5. TP and SL must be valid relative to live price.
6. Profit distance must exceed mode/category/optimizer minimum.
7. True RR must exceed tuned target RR.
8. Strategy-specific gate must pass.
9. Live permission must pass optimizer and performance block.
10. Duplicate same-candle and cooldown checks must pass.
11. Opposite position check must pass.
12. Symbol reservation must pass.
13. Risk-based leverage and confidence sizing are computed.
14. Expected edge versus cost must pass.
15. Safety halt and unprotected-position checks must pass.
16. Bounded limit entry is attempted.
17. If filled, exact-fill TP/SL protection must be placed and verified.

## Position Sizing Logic

The sizing stack has two layers:

### Confidence margin

`get_confidence_score()` starts from a neutral score and adjusts by:

- Profit factor.
- Win rate.
- Sample size weight.
- Weak PF/win-rate penalty.
- Category margin multiplier.

`build_sizing_plan()` maps confidence into target margin:

- Base margin: 60U.
- Margin increases only half as fast as confidence above 1.0.
- Final margin is clamped between 20U and 150U.
- Available USDT can cap the target to a small account percentage.

### Leverage cap

`risk_based_leverage_cap()` limits leverage by:

```text
max_planned_loss / (margin * (stop_distance_pct + fee + slippage))
```

Non-major symbols are capped more conservatively than BTC/ETH-like assets.

## Performance Block

When a mode has enough mature samples:

```text
if total_trades >= 30 and (PF < 1.05 or expectancy < 0):
    block the mode
```

This is a good capital-protection rule, but currently it is mode-level. It should evolve into:

```text
Mode + Setup + Category + Direction + Session + Volatility Regime + Score Bucket
```

Without this partition, a good setup can be hidden by a bad setup inside the same mode, or a bad symbol category can contaminate the whole mode.

## Execution Cost Gate

The execution cost gate computes:

- Gross target USDT.
- Estimated fee/slippage cost.
- Expected net.
- Required gross target.

The candidate is blocked if gross target cannot cover estimated cost and minimum net edge.

This is one of the strongest current protections because it prevents tiny TP targets from being falsely counted as profitable before fees.

## Protection Logic

The protection chain is strict:

1. Entry uses bounded limit, no market chase.
2. After fill, the plan is rebased to the actual fill price.
3. SL and TP validity are rechecked.
4. `place_exact_fill_protection()` places protection based on exact filled size.
5. `ensure_live_position_fully_protected()` verifies exchange-side protection.
6. If protection placement or verification fails, the engine triggers emergency close or halt.
7. Existing unprotected active or exchange positions block new entries.

This is correct behavior for a demo/live bot. It can reduce trade frequency, but it prevents compounding unmanaged exposure.

## Exit Logic

Exit management currently lives inside `engine.py`, not a separate `FastExitManager`.

Current behaviors include:

- SqueezeHunter partial take profit at 1R-like progress.
- Breakeven and profit lock thresholds based on MFE/R progress.
- Runner mode after sufficient progress.
- Trailing stop update.
- Optional TP removal when runner progress reaches configured threshold.
- Protection reconciliation after trailing updates.

Gap:

- There is no isolated fast-exit simulator.
- No formal comparison exists for static TP/SL versus Time Stop, Momentum Decay, Structure Failure, Edge Decay, or Hybrid Exit.
- MFE/MAE and time-to-MFE are not yet persisted in a dedicated short-scalp performance store.

## Current Safety Failure Modes

| Failure mode | Current response | Risk |
| --- | --- | --- |
| Existing active trade lacks verified TP/SL | New entries paused | Lowers opportunity count but protects account |
| OKX live position lacks verified TP/SL | New entries paused | Correct safety behavior |
| Protection rejected after fill | Emergency close/halt | Correct but must be monitored |
| Protection verification timeout/failure | Emergency close/halt | Correct but can close valid positions during API instability |
| Expected target too small after costs | Candidate blocked | Correct |
| Mode PF below mature threshold | Mode blocked | Good, but too coarse |
| Router score ambiguous | NO_TRADE | Good, but must be measured |

## Missing Risk Controls for Short Scalp Mode

Before any live short-scalp trading, these should be added:

- `MAX_SCALP_LOSS_PER_TRADE_U`
- `MAX_SCALP_LOSS_PER_HOUR_U`
- `MAX_SCALP_LOSS_PER_DAY_U`
- `MAX_SCALP_CONSECUTIVE_LOSSES`
- `MAX_CORRELATED_SYMBOL_EXPOSURE`
- `MIN_NET_EDGE_BPS`
- `MAX_ALLOWED_SPREAD_BPS`
- `MAX_ALLOWED_SLIPPAGE_BPS`
- `COST_SAFETY_MULTIPLIER`
- Setup ownership TTL.
- Shadow-only default state.

## Recommendations

1. Keep the current protection-first entry flow unchanged until observability and replay exist.
2. Add blocker event logging before changing thresholds.
3. Split fast exits into `fast_exit_manager.py` only after shadow/replay instrumentation is in place.
4. Add setup-level performance partitions before allowing optimizer changes to affect live sizing.
5. Require OOS/replay PASS before any Phase 6 limited-live setup is promoted.
